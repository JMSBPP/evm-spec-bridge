  <read_first>

  <teaching>
    The reason to split is not tidiness, it is feedback latency. The seam guard costs 0.34 s of
    Stack time; the build costs minutes to tens of minutes. If they share a job, a seam violation is
    reported only after the runner has installed GHC, restored a cache and possibly compiled the
    cairo tree. Separating them means the cheapest, most decisive signal arrives first.

    It also preserves the D4 circularity argument at the CI level: the seam job must be able to run
    and report even when the build job is red. Same job means same fate.
  </teaching>
  <decision>How is the gate decomposed into jobs?</decision>

    ordering consequence is worth stating. Three jobs: `seam` (seconds, no dependencies), `build`

  <read_first>
    - .planning/phases/01-repo-skeleton-component-seams-ci-floor/01-RESEARCH.md (section "Code Examples → CI workflow", the header block; and "Pitfall 8: `permissions:` at workflow level is inherited, not per-job, unless you say so")

  <teaching>
    Two things here are decisions dressed as boilerplate.

    Running on `push` as well as `pull_request` is deliberately broader than the consumer repo's
    PR-only gate. Work happens in `feat/*` worktrees, and a gate that only runs at promotion time
    discovers breakage after the work is finished rather than while it is happening. The cost is
    more CI minutes; the benefit is that "it worked locally" gets falsified early.

    `permissions: contents: read` at workflow level: permissions are inherited by every job unless
    the job overrides them. Putting `packages: write` at the top would grant it to the seam and
    build jobs, which have no business publishing anything. Worse, on a fork PR the write scope is
    silently downgraded anyway — so a top-level `packages: write` reads as protection that does not
    exist. Least privilege at the top, widened only in the one job that publishes, also documents
    which job that is.
  </teaching>

  <name>Task 4: The build job — compile everything, run tasty, gate on drift</name>
  <read_first>
    - .planning/phases/01-repo-skeleton-component-seams-ci-floor/01-RESEARCH.md (section "Code Examples → CI workflow", the `build:` job; "M7"; "Pitfall 5: The Actions cache is 10 GB per repo, LRU, and expires in 7 days")
    - scripts/hpack-drift.sh
    - justfile
  </read_first>
  <teaching>
    Two subtleties in the cache key.

    First, why it is complete: a spec bump changes `commit:` in `stack.yaml` *and* both the
    `commit:` and the `pantry-tree` sha256 in `stack.yaml.lock`. So hashing those two files
    genuinely invalidates the cache when the spec moves. PITFALLS.md #12 warned that a source-dep
    bump can leave a freeze file unchanged, serving a stale cached build — that is true of
    `cabal.project.freeze` plus submodules and false here. The lesson generalises: verify an
    inherited warning against your actual tool before you design around it.

    Second, the 10 GB ceiling. The Actions cache is 10 GB per repository with LRU eviction and a
    7-day expiry. A Stack root carrying LTS 24.55 plus the Chart-cairo tree, plus a GHC bindist,
    plus seven `.stack-work` directories, can plausibly approach it — and once it does, caches evict
    each other round-robin and every run is silently cold. The classic symptom is "cache hit
    reported, build time unchanged". That is why this job prints `du -sh` alongside the timings:
    cache size is folklore too, and Phase 1's job is to convert folklore into numbers.
  </teaching>
  <action>
    Append the `build` job following RESEARCH.md §"Code Examples → CI workflow" verbatim. Its
    ordered contents:

    1. `actions/checkout@v5`
    2. apt step installing exactly `libcairo2-dev libpango1.0-dev libglib2.0-dev pkg-config`, with a
       comment saying these arrive via the spec LIBRARY, not just its executable
    3. `haskell-actions/setup@v2` with `stack-version: '3.11.1'` and `ghc-version: '9.10.3'`,
       IMMEDIATELY followed by a step that makes system-GHC the global default:

       ```yaml
       # haskell-actions/setup does NOT write system-ghc into any Stack config. Stack's
       # defaults are system-ghc:false / install-ghc:true, so ANY bare `stack` invocation
       # downloads and unpacks its own GHC 9.10.3. The scripts this gate calls
       # (seam-negative-test.sh, hpack-drift.sh) run bare `stack` -- so without this the
       # "0.34 second" seam job takes minutes and a bindist inflates the cached ~/.stack,
       # corrupting the very number this plan is here to measure.
       - name: Make system-GHC the global default
         run: |
           stack config set system-ghc true --global
           stack config set install-ghc false --global
       ```

       With this in place, DROP `--system-ghc --no-install-ghc` from every command in the
       workflow. That restores the property 01-05 sells the justfile on: the strings CI runs
       are the strings `just` runs.
    4. `actions/cache@v4` with `id: stackcache`, paths `~/.stack`, `.stack-work`,
       `components/*/.stack-work`, key
       `stack-${{ runner.os }}-ghc9.10.3-${{ hashFiles('stack.yaml', 'stack.yaml.lock', 'components/*/package.yaml') }}-${{ github.run_id }}`
       and `restore-keys: stack-${{ runner.os }}-ghc9.10.3-`

       The `-${{ github.run_id }}` suffix is LOAD-BEARING, not noise. **Actions caches are
       immutable — "You cannot change the contents of an existing cache."** Without a unique
       suffix, the hashFiles inputs stop changing after 01-03, so the cache written by the FIRST
       run (a cold, partial one) is frozen for its whole 7-day life and never improves. `restore-keys`
       still matches the prefix, so every run restores the newest previous cache and then saves a
       fresh, better one. Without this, the cross-run warm build number this phase exists to publish
       is systematically wrong.
    5. "build (timed)" — record epoch seconds, run
       `stack --system-ghc --no-install-ghc build --test --no-run-tests --pedantic`, write
       `T_BUILD` to `$GITHUB_ENV`
    6. "warm rebuild (timed)" — the same build again, writing `T_WARM`. The delta between these two
       numbers is the incremental-rebuild cost, which is what a developer actually experiences.
    7. "tasty" — `stack --system-ghc --no-install-ghc test`
    8. "hpack drift gate" — `./scripts/hpack-drift.sh` (the same string as `just drift`)
    9. "record build times and cache sizes" with `if: always()`, writing a markdown table to
       `$GITHUB_STEP_SUMMARY` containing: cache state (derived from `steps.stackcache.outputs.cache-hit`
       and `cache-matched-key` — exact hit, partial restore, or miss), `T_BUILD`, `T_WARM`,
       `du -sh ~/.stack`, and `du -sch .stack-work components/*/.stack-work`

    **`--pedantic` must be on BOTH builds or NEITHER — do not vary it between them.**
    `--pedantic` adds `-Wall -Werror` to local packages, which changes their GHC options and
    therefore their Stack configure hash. Dropping it for the second build makes Stack RECOMPILE
    all seven local packages, so `T_WARM` would be a full-recompile time wearing an
    incremental-rebuild label — a number that is folklore with a timestamp on it. Keep
    `--pedantic` on both.

    `--pedantic` applies to local packages only. It turns warnings into errors for the seven local
    packages; extra-deps are not built pedantically, so `cfmm-scratchpad`'s own warnings are not
    ours. Say that explicitly — otherwise the first red build looks like the spec's fault.

    `if: always()` on the measurement step matters: a red build is exactly when you most want to
    know whether it was cold.
  </action>

        cold-build-benchmark:
          name: cold build benchmark (manual)
          if: github.event_name == 'workflow_dispatch'
          runs-on: ubuntu-latest
          steps:
            # Identical to `build`, but with NO actions/cache step at all -- so this includes
