<objective>
Publish the container image to GHCR from CI — and handle the permission asymmetry that would
otherwise make every promotion PR red.

Purpose: DIST-04 requires publishing the image to GHCR. The complication is real and was the most
likely blocker in the research: a `pull_request` from the `JMSBPP` fork into `d2p-finance` runs with
a **read-only** token, `packages: write` is silently downgraded, and an unconditional push 403s.
Output: an `image` job that builds on every trigger and pushes only on `push`, a published image,
and a verified anonymous pull.
</objective>

<task type="checkpoint:decision" id="01-08-T2" gate="blocking">
  <name>Task 2: The fork-PR permission asymmetry — build always, push only on push</name>
  <read_first>
    - .planning/phases/01-repo-skeleton-component-seams-ci-floor/01-RESEARCH.md (section "The Fork PR / GHCR Permission Problem (Q6)" in full)
    - .planning/REQUIREMENTS.md (DIST-03 and DIST-04 together)
    - .github/workflows/ci.yml
  </read_first>
  <teaching>
    This is the most consequential CI fact in the phase, and it is invisible until it bites.

    A `pull_request` whose head repository differs from its base repository — a fork PR — runs with
    a **read-only** `GITHUB_TOKEN` and receives no secrets. This is a security property, not a
    setting: GitHub cannot let arbitrary fork contributors obtain write credentials by opening a PR.
    Critically, `permissions: packages: write` in the workflow file is not an error in that context;
    it is **silently downgraded**. So the file *claims* a capability the run does not have, and the
    failure surfaces much later as a runtime 403 in `docker/login-action` or the push step.

    That matters here because a fork PR is not an edge case — it is the DIST-03 promotion path.
    Every single promotion from `JMSBPP:develop` to `d2p-finance:main` is a fork PR. A workflow that
    unconditionally pushes would make every promotion PR red, permanently.

    The resolution keeps both properties: `push: ${{ github.event_name == 'push' }}` and
    `load: ${{ github.event_name != 'push' }}`. The Dockerfile is still genuinely *gated* on the PR
    — a broken Dockerfile goes red at promotion time — while the run never attempts an operation
    its token cannot perform. DIST-04 is still satisfied because every change lands on the fork's
    `develop` via a push, and that push publishes.

    The transferable idea: when a capability is context-dependent, gate on the context rather than
    on the permission declaration. Declaring the permission does not obtain it.
  </teaching>
  <decision>How does the image job handle the fork-PR token restriction?</decision>
  <context>
    A related sub-decision: registry cache (`cache-to: type=registry`) also needs write. `type=gha`
    uses the Actions cache service, which is read-only on fork PRs — writes are skipped rather than
    fatal. And the Actions cache ceiling of 10 GB is SHARED with the build job's `~/.stack` cache,
    so a `mode=max` BuildKit cache here can evict the Stack cache and make every build cold.
  </context>
  <options>
    <option id="build-always-push-on-push">
      <name>Build on every trigger; push only when github.event_name == 'push' (recommendation)</name>
      <pros>Promotion PRs stay green; the Dockerfile is still gated on PRs; no operation is attempted that the token cannot perform</pros>
      <cons>The image is never published from a PR — acceptable, since every change reaches develop by push</cons>
    </option>
    <option id="push-always">
      <name>Push unconditionally</name>
      <pros>Simplest YAML</pros>
      <cons>Every fork PR into d2p-finance goes red with a 403 — i.e. every promotion, forever</cons>
    </option>
    <option id="skip-image-on-pr">
      <name>Skip the image job entirely on pull_request</name>
      <pros>No 403</pros>
      <cons>A broken Dockerfile is not caught at promotion time, which is exactly when it should be</cons>
    </option>
  </options>
  <acceptance_criteria>

  <name>Task 4: Write the image job</name>
  <read_first>
    - .planning/phases/01-repo-skeleton-component-seams-ci-floor/01-RESEARCH.md (section "Code Examples → CI workflow", the `image:` job; and "Pitfall 8")
    - .planning/phases/01-repo-skeleton-component-seams-ci-floor/01-01-PROBE-NOTES.md (`## Fork-PR GHCR asymmetry`, `## D7`)
    - .github/workflows/ci.yml
    - docker/Dockerfile
  </read_first>
  <action>
    Append the `image` job to `.github/workflows/ci.yml`, following RESEARCH.md verbatim:

        image:
          name: container image
          needs: [seam, build]
          runs-on: ubuntu-latest
          permissions:
            contents: read
            packages: write       # honoured on push; silently downgraded on a fork PR
          steps:
            - uses: actions/checkout@v5
            - uses: docker/setup-buildx-action@v3
            # An OCI tag MUST match [a-zA-Z0-9_][a-zA-Z0-9._-]{0,127} -- NO SLASH.
            # github.ref_name is `develop` on a develop push, but `feat/x` on a feature
            # push and `<pr_number>/merge` on a pull_request. Using it raw makes the job
            # fail at tag-parse time on every PR and every feat/* push -- i.e. on every
            # path except the one this plan happens to exercise.
            - name: Compute a slash-free ref tag
              id: reftag
              run: echo "safe=${GITHUB_REF_NAME//\//-}" >> "$GITHUB_OUTPUT"
            - name: Log in to GHCR
              if: github.event_name == 'push'
              uses: docker/login-action@v3
              with:
                registry: ghcr.io
                username: ${{ github.actor }}
                password: ${{ secrets.GITHUB_TOKEN }}
            - name: Build (always) and push (push events only)
              id: build
              uses: docker/build-push-action@v6
              with:
                context: .
                file: docker/Dockerfile
                platforms: linux/amd64
                # A fork PR into d2p-finance cannot push. Build it anyway so a broken
                # Dockerfile still goes red at promotion time.
                push: ${{ github.event_name == 'push' }}
                load: true
                tags: |
                  ${{ env.IMAGE }}:sha-${{ github.sha }}
                  ${{ env.IMAGE }}:${{ steps.reftag.outputs.safe }}
                labels: |
                  org.opencontainers.image.source=https://github.com/${{ github.repository }}
                  org.opencontainers.image.revision=${{ github.sha }}
                cache-from: type=gha
                cache-to: ${{ github.event_name == 'push' && 'type=gha,mode=min' || '' }}
            # Proves the runtime stage actually has what the binary links (libgmp).
            # A Dockerfile that builds but produces a binary that cannot start is a false green.
            # `load` must be true for the smoke test to exercise the LOCAL image. With
            # push:true/load:false the image is not in the daemon and `docker run` would
            # silently pull it back from GHCR -- turning a runtime check into a registry
            # round-trip on the path that matters most.
            - name: smoke -- the shipped binary runs
              run: docker run --rm ${{ env.IMAGE }}:sha-${{ github.sha }} --version

    Four details worth naming as you write them:
    - `needs: [seam, build]` — do not spend image-build minutes when the seam or the compile is
      already red.
    - `permissions:` appears at JOB level here and nowhere else, which documents that this is the
      only job that publishes.
    - `org.opencontainers.image.source` is what makes the published package link back to the
      repository in GitHub's UI. Without it the package appears orphaned. `github.repository` IS
      correct here — it is a URL, not a Docker reference.
    - `mode=min` not `mode=max`, and only on push, because the 10 GB Actions cache is shared with
      the build job's `~/.stack` and a `mode=max` BuildKit cache can evict it into permanent
      coldness (Pitfall 5).
  </action>
  <verify>
    <automated>grep -q 'needs: \[seam, build\]' .github/workflows/ci.yml &amp;&amp; grep -q "push: \${{ github.event_name == 'push' }}" .github/workflows/ci.yml &amp;&amp; grep -q 'org.opencontainers.image.source' .github/workflows/ci.yml &amp;&amp; grep -q 'mode=min' .github/workflows/ci.yml</automated>
  </verify>
  <acceptance_criteria>
    - The `image` job contains `needs: [seam, build]`
    - It contains the literal string `push: ${{ github.event_name == 'push' }}`
    - It contains the literal string `load: ${{ github.event_name != 'push' }}`
    - The login step carries `if: github.event_name == 'push'`
    - `packages: write` appears exactly once in the whole file, inside the `image` job's `permissions:` block

    - It contains `platforms: linux/amd64` and no buildx matrix
    - `grep -c 'mode=max' .github/workflows/ci.yml` equals `0`
    - It contains a smoke step running `docker run --rm` with `--version`
  </acceptance_criteria>
  <done>The image job builds on every trigger, pushes and logs in only on push events, carries job-scoped write permission, labels the package, and smoke-tests the shipped binary.</done>

    So this is an intentional human gate on an irreversible, security-relevant action, and the plan
    surfaces it rather than assuming the workflow handled it. The acceptance criterion is not the UI
    click — it is the credential-free pull that proves the click had the intended effect.
