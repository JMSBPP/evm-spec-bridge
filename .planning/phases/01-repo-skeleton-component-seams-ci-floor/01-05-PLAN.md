same shape the generated Solidity gets in Phase 8 — establishing it now makes both one habit
rather than two.

  <teaching>
    `tasty-discover` finds tests by filename and function-name prefix (`unit_`, `prop_`, `test_`).
    Get the prefix wrong, put a module in the wrong directory, or forget it in `other-modules`, and
    the suite runs zero tests and exits 0. Green, fast, and meaningless.

    That failure mode — "silently tested nothing" — is this project's stated characteristic failure
    mode, and paying for it to save one line per module is a bad trade. The concern CONTEXT.md
    raised ("later phases add cases rather than also wiring up a runner") is satisfied by an
    explicit `Main.hs`: adding a test module is one `import` plus one list entry. That is not wiring
    up a runner.

    General shape: prefer mechanisms whose failure mode is loud. Discovery magic fails silently by
    construction.
  </teaching>
  <decision>How does the tasty suite find its tests?</decision>
  <context>

  <name>Task 4: D8 — the drift gate, and why the Stack version must be pinned</name>
  <read_first>
    - .planning/phases/01-repo-skeleton-component-seams-ci-floor/01-RESEARCH.md (section "Pitfall 2: hpack version skew makes the drift gate red for a reason unrelated to drift", "M6", "Pattern 3: hpack drift gate", and row D8 of "Decision Points to Surface During Execution")
    - components/protocol/evm-spec-bridge-protocol.cabal (line 1)

  <teaching>
    A byte-diff gate is trustworthy precisely because it compares bytes — it cannot be argued with.
    The cost is that every byte counts, including bytes nobody thinks of as content. Line 1 of every
    generated .cabal is `-- This file has been generated from package.yaml by hpack version 0.39.6.`
    A CI runner with a different Stack (and therefore a different bundled hpack) rewrites that line,
    and the gate goes red with no semantic change whatsoever.

    Three consequences, all of which are decisions:
    1. Pin `stack-version: '3.11.1'` in CI. Never `latest`. (The spec repo's own CI uses `latest`
       and carries this latent bomb — worth mentioning to its owner.)
    2. Never run hpack inside the Docker image: copy the committed `.cabal` files and NOT the
       `package.yaml` files, so the image's Stack version cannot matter. Plan 01-06 does this.
    3. Do NOT strip the header before diffing. That weakens a gate to work around a version pin,
       which trades a loud failure for a quiet one.

    Diagnostic to remember: a `.cabal` diff whose only hunk is line 1 or 3 is version skew, not
    drift.
  </teaching>
  <what-built>
    `scripts/hpack-drift.sh`:

        #!/usr/bin/env bash
        # scripts/hpack-drift.sh
        #
        # DIST-04. The committed .cabal files must match what hpack generates from package.yaml.
        # Uses the FULL config so all seven packages are covered (stack-core.yaml would only
        # regenerate six). Requires the PINNED stack version -- the .cabal header is version-
        # stamped, so a different hpack rewrites line 1 and this gate goes red for no reason.
        set -euo pipefail
        REPO_ROOT="$(cd "$(dirname "${BASH_SOURCE[0]}")/.." && pwd)"
        cd "$REPO_ROOT"
        stack build --dry-run >/dev/null
        git diff --exit-code -- '**/*.cabal' && test -z "$(git status --porcelain -- '*.cabal')"
  </what-built>
  <how-to-verify>
    1. Create the script, `chmod +x`, and run it on a clean tree: must exit 0 and print nothing.
    2. Now make it go red for a REAL reason. Edit `components/codegen/package.yaml` — change the

    6. Confirm `git status --porcelain` is empty before finishing.
  </how-to-verify>

  <action>
    D10 is explicit discretion in CONTEXT.md, so this is mechanical. The reason to bother: when the
    gate and the human run different strings, a green local run stops predicting a green CI run, and
    the difference is discovered at the worst moment.

    Create `justfile` at the repository root:

        # Local commands and CI steps are the SAME strings. If they diverge, a green
        # local run stops predicting a green gate.
        default:
            @just --list

        # CFMM-01 positive control -- ~0.3s
        seam:
            ./scripts/seam-guard.sh

        # CFMM-01 proof the guard fires
        seam-negative:
            ./scripts/seam-negative-test.sh

        # DIST-04 generated-artifact gate
        drift:
            ./scripts/hpack-drift.sh

        build:
            stack build --test --no-run-tests --pedantic

        test:
            stack test

        # Everything the gate runs, in gate order (cheap first)
        gate: seam seam-negative build test drift

    Verify `just --list` works. If `just` is not installed, note it in PROBE-NOTES and install it
    (`pacman -S just`) — the justfile is a convenience, but an uninstallable convenience is friction.
    CI will call the scripts directly, not `just`, so the gate never depends on `just` being present
    on the runner.
  </action>
