Prove the guard fires — and then prove the proof works.

A guard nobody has seen fire is a guard being trusted, not one that has been verified. Untested
guards producing false greens is this project's central failure mode, so the mechanism built to
prevent it must not itself be taken on faith.

Purpose: CFMM-01's acceptance is not "the config exists" but "the forbidden edge was added and the
build went red for the right reason".
Output: two shell scripts, plus a live demonstration that ends with the negative test deliberately
broken and observed going red.

<task type="checkpoint:decision" id="01-04-T1" gate="blocking">
  <name>Task 1: D4 — is the negative test a shell script or a tasty case?</name>
  <read_first>
    - .planning/phases/01-repo-skeleton-component-seams-ci-floor/01-RESEARCH.md (section "Pitfall 3: Running the seam negative test inside `stack test`", and row D4 of "Decision Points to Surface During Execution")
    - .planning/phases/01-repo-skeleton-component-seams-ci-floor/01-VALIDATION.md (section "Wave 0 Requirements", fourth bullet)
  </read_first>
  <teaching>
    This is the transferable idea of the whole phase, and it is worth stating slowly.

    A test of the build, run inside the build, never runs when the build breaks.

    Making the negative test a tasty case is the natural instinct — it is a test, tests live in the
    test suite. But that test can only execute after the test suite compiles, which requires the
    build to succeed. So in exactly the scenario the test exists to detect — the seam is broken in a
    way that also breaks the build — the test never runs, and CI reports "build failure" instead of
    "seam violation". The signal the test exists to produce is the one signal it structurally cannot
    produce.

    Two lesser reasons reinforce it: a nested stack process spawned from inside `stack test` shares
    STACK_ROOT and may contend on pantry/project locks; and it converts a 0.34 s fail-fast check
    into one gated behind a full compile.

    The general rule: a check on property P must not depend on P. Keep the meta-level outside.
  </teaching>
  <decision>Where does the seam negative test live?</decision>
  <context>
    CONTEXT.md wants a tasty scaffold from Phase 1 so later phases add cases rather than wire up a
    runner. That is a real goal and it is satisfied in plan 01-05. This decision is about a
    different kind of check: tasty is for Haskell-level properties of code that compiled; the seam
    guard is a property of the build system itself.
  </context>
  <options>
    <option id="shell-script">
      <name>A shell script in scripts/, invoked by a dedicated CI job that runs BEFORE the build job</name>
      <pros>Runs even when the build is broken — the only case that matters; 0.34 s fail-fast; no nested Stack</pros>
      <cons>Not discoverable from `stack test`; needs its own CI job (which is wanted anyway — see D9)</cons>
    </option>
    <option id="tasty-case">
      <name>A tasty case that shells out to stack</name>
      <pros>One place to run all checks</pros>
      <cons>Circular — cannot run when the build is broken. Nested Stack lock contention. Slow.</cons>
    </option>
  </options>
  <acceptance_criteria>

    - The user can restate, unprompted, why a test of the build must not live inside the build

<task type="auto" id="01-04-T3">
  <name>Task 3: Write scripts/seam-negative-test.sh with a three-part assertion</name>
  <read_first>
    - .planning/phases/01-repo-skeleton-component-seams-ci-floor/01-RESEARCH.md (section "Code Examples → The seam guard + negative test script", and "Pitfall 1: The negative test passes because the build failed for the wrong reason")
    - scripts/seam-guard.sh
    - components/protocol/package.yaml (the victim file the script mutates in a scratch copy)
  </read_first>
  <teaching>
    Exit code 1 is the least informative signal a build system produces. A typo in a .hs file, a
    network blip fetching the snapshot, a full disk, or a missing GHC all produce exit 1 — and a
    negative test that asserts only "non-zero" would report "guard fired" for every one of them. It
    would be asserted green while actually broken: precisely the silent-false-green class this
    project exists to kill, reproduced inside the anti-false-green mechanism itself.

    Hence three assertions, not one:
    1. CONTROL — the unmodified tree must resolve green first. If the control is red, the
       environment is broken and the guard was never tested; abort with a distinct message.
    2. NEGATIVE — the violated tree must fail AND the output must contain S-4804 AND
       cfmm-scratchpad AND the violated package's name. Not merely non-zero.
    3. CONTRAST — the same violated tree must still resolve green under full stack.yaml. This
       proves we measured the seam and not a broken tree.
  </teaching>
  <action>
    Write `scripts/seam-negative-test.sh` following RESEARCH.md §"Code Examples" verbatim, with
    `VICTIM="components/protocol/package.yaml"` and the three greps `S-4804`, `cfmm-scratchpad`,
    `evm-spec-bridge-protocol`.

    Three implementation notes that matter:

    - Never mutate the working tree. Copy to `mktemp -d` using
      `tar --exclude='.git' --exclude='.stack-work' --exclude='*/.stack-work'` piped into the
      scratch dir, with `trap 'rm -rf "$SCRATCH"' EXIT`. An interrupted in-place edit would leave
      the repo carrying the forbidden edge. `git worktree add` was considered and rejected: it
      requires the violation to exist on a committed branch, which is the one state we must never
      create.
    - Assert the injection took before trusting the result:
      `grep -q 'cfmm-scratchpad' "$SCRATCH/$VICTIM" || { echo "FAIL: injection did not take"; exit 1; }`
      An injection that silently no-ops would make the negative test pass by measuring nothing.
    - The research script uses python3 for the injection. Confirm `python3 --version` works both
      locally and on ubuntu-latest (it does), or substitute a sed/awk equivalent that inserts
      `- cfmm-scratchpad` immediately after the first `dependencies:` line. If substituting, keep
      the "assert the injection took" grep — it is what makes either implementation safe.

    Finish with `chmod +x scripts/seam-negative-test.sh`. Do not run it yet; Task 4 runs it.
  </action>
  <verify>
    <automated>test -x scripts/seam-negative-test.sh &amp;&amp; grep -q 'S-4804' scripts/seam-negative-test.sh &amp;&amp; grep -q 'mktemp -d' scripts/seam-negative-test.sh &amp;&amp; grep -q 'injection did not take' scripts/seam-negative-test.sh</automated>

<task type="checkpoint:human-verify" id="01-04-T5" gate="blocking">
  <name>Task 5: THE META-CHECK — break the guard on purpose and watch the negative test go red</name>
  <read_first>
    - .planning/phases/01-repo-skeleton-component-seams-ci-floor/01-RESEARCH.md (section "Pitfall 1", the paragraph beginning "Meta-check worth doing once, live, with the user")
    - stack-core.yaml
    - scripts/seam-negative-test.sh
  </read_first>
  <teaching>
    Task 4 proved the guard fires. It did not prove the negative test would *notice* if the guard
    stopped firing. Those are different claims, and only the second one makes the test worth
    running on every push.

    The way to establish it is to disable the guard and confirm the test goes red. This is testing
    the test — the same move as commenting out an assertion to confirm it was actually load-bearing.
    RESEARCH.md calls it the single most instructive thirty seconds in this phase.

    Notice what happens to the failure *message* as well as the exit code: the test should fail at
    the NEGATIVE stage with "guard did NOT fire (exit 0)", not at CONTROL and not at CONTRAST. A
    test that goes red is not enough; it must go red in the right place, or the next person will
    mis-diagnose it.
  </teaching>
  <what-built>
    Nothing new. This deliberately sabotages `stack-core.yaml` for sixty seconds to establish that
    the negative test has detection power, then restores it.
  </what-built>
  <how-to-verify>
    1. Record the current file so restoration is provable:
       `sha256sum stack-core.yaml | tee /tmp/core-before.sha`
    2. Sabotage it — replace `extra-deps: []` with the real spec extra-dep, making `stack-core.yaml`
       semantically identical to `stack.yaml` and the guard vacuous:

           extra-deps:
           - git: https://github.com/JMSBPP/cfmm-vol-markets-spec.git
             commit: <the same SHA as stack.yaml>

    3. Re-run: `./scripts/seam-negative-test.sh; echo "exit=$?"`
    4. Confirm it goes RED, at the NEGATIVE stage, with `exit=1` and a message containing
       `FAIL: guard did NOT fire (exit 0)`. Say aloud why: with the spec now resolvable in the
       spec-less config, the injected forbidden edge resolves fine, so the guard has nothing to
       catch. This is exactly the state Pitfall 7 warns about, produced deliberately.
    5. Restore: `git checkout -- stack-core.yaml`
    6. Prove restoration: `sha256sum stack-core.yaml` matches `/tmp/core-before.sha`, and
       `git status --porcelain -- components/ stack.yaml stack-core.yaml` prints nothing.
    7. Re-run the negative test once more and confirm `SEAM GUARD VERIFIED` returns.
    8. Record all of this in `01-01-PROBE-NOTES.md` under `## Meta-check — testing the test`,
       including the red output verbatim.
  </how-to-verify>
  <acceptance_criteria>
    - With the sabotaged `stack-core.yaml`, `./scripts/seam-negative-test.sh` exits `1`
    - That run's output contains `FAIL: guard did NOT fire (exit 0)`
    - That run's output does NOT contain `FAIL(control)` (it must fail at NEGATIVE, not CONTROL)
    - After `git checkout -- stack-core.yaml`, `sha256sum stack-core.yaml` matches `/tmp/core-before.sha`
    - After restoration, `./scripts/seam-negative-test.sh` exits 0 and prints `SEAM GUARD VERIFIED`
    - `git status --porcelain -- components/ stack.yaml stack-core.yaml` produces no output at the end of this task
    - `01-01-PROBE-NOTES.md` contains `## Meta-check — testing the test` with the red output pasted
  </acceptance_criteria>
  <resume-signal>Type `approved` once the test has been seen RED at the NEGATIVE stage and GREEN again after restore</resume-signal>
  <done>The negative test has been proven to have detection power, and `stack-core.yaml` is byte-identical to its committed state.</done>
