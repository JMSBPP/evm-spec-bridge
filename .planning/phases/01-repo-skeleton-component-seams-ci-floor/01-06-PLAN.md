code — so that GHC-in-a-container, cairo resolution at build time, and the multi-stage split are

writable against it.

<task type="checkpoint:human-verify" id="01-06-T3" gate="blocking">
  <name>Task 3: D5 — run ldd and find out what the binary actually links</name>
  <read_first>
    - .planning/phases/01-repo-skeleton-component-seams-ci-floor/01-RESEARCH.md (section "M9 — a GHC 9.10.3 binary's runtime shared-library set", and row D5 of "Decision Points to Surface During Execution")
    - components/transport/package.yaml
  </read_first>
  <teaching>
    The question "what goes in the runtime image?" is almost always answered by guessing, and the
    guess is almost always "everything the build needed". That is how 6 GB runtime images happen.

    The correct move is to ask the binary. `ldd` lists exactly the shared objects the dynamic loader
    will need. For a `-threaded` GHC 9.10.3 binary the answer is small: `libm`, `libgmp.so.10`,
    `libc`, plus the vDSO and the loader. libffi is statically linked. No libtinfo, no zlib, and —
    critically — **no cairo and no pango**, even though the build needed both.

    So cairo is a BUILD-time dependency only. It enters the graph through `cfmm-vol-markets-spec`'s
    package-level `Chart-cairo`, which the *library* inherits, so anything compiling against the
    spec needs the headers. But the Phase 1 binary does not link `cfmm-adapter`, so nothing cairo
    survives into the artifact. Write down that Phase 11 revisits this: once the shipped executable
    genuinely links the adapter, the runtime stage's dependency set must be re-measured, not
    assumed.
  </teaching>
  <what-built>
    The `evm-spec-bridge` binary from Task 2.
  </what-built>
  <how-to-verify>
    Run, live:

        BIN=$(stack path --local-install-root)/bin/evm-spec-bridge
        file "$BIN"
        ldd "$BIN"
        ls -lh "$BIN"

    Confirm the `ldd` output lists `libm.so.6`, `libgmp.so.10`, `libc.so.6` and nothing named
    `cairo`, `pango`, `glib`, `tinfo` or `z`. Then check the negative explicitly:

        ldd "$BIN" | grep -Ec 'cairo|pango|glib'    # must print 0

    **One thing `ldd` CANNOT tell you, and it is a latent false green.** `debian:bookworm-slim`
    ships no locale. GHC derives handle encoding from the locale and falls back to ASCII, so the
    first non-ASCII byte a JSON-RPC server writes dies with
    `commitBuffer: invalid argument (invalid character)`. Phase 1's ASCII `--version` passes
    happily, so without `ENV LANG=C.UTF-8` this ships silently into Phases 4-5 and surfaces as a
    transport failure caused by an encoding bug. `C.UTF-8` is built into glibc 2.36 on bookworm —
    no `locales` package needed. Note what this means: `ldd` determines the SHARED LIBRARIES the
    runtime needs, not everything the runtime needs.

    State the conclusion aloud: the runtime stage is `debian:bookworm-slim` plus `libgmp10`
    (and `ca-certificates` for any future TLS). Record the full `ldd` output, the binary size, and
    `DECISION: no-cairo-at-runtime; revisit at Phase 11` in `01-01-PROBE-NOTES.md` under `## D5`.
  </how-to-verify>
  <acceptance_criteria>
    - `ldd` output for the built binary contains `libgmp.so.10`, `libm.so.6` and `libc.so.6`
    - `ldd "$BIN" | grep -Ec 'cairo|pango|glib'` prints `0`
    - `01-01-PROBE-NOTES.md` contains `## D5`, the pasted `ldd` output, the binary size, and the literal string `revisit at Phase 11`

  <action>
    Create `docker/Dockerfile` exactly as given in RESEARCH.md §"Code Examples → Multi-stage
    Dockerfile". Four properties are load-bearing and each has a comment in the file explaining
    itself:

    1. **Builder base `haskell:9.10.3-bookworm`.** Pinned to the compiler LTS 24.55 declares, so the
       image and CI cannot disagree about GHC. It already sets `system-ghc: true` /
       `install-ghc: false`, so Stack will not download a second GHC. 0.67 GB, versus 6.24 GB for
       `fpco/stack-build:lts-24.55`.

    2. **The cairo apt set in the builder only:**
       `libcairo2-dev libpango1.0-dev libglib2.0-dev pkg-config`, followed by
       `rm -rf /var/lib/apt/lists/*`.

    3. **The dependency layer copies `.cabal` files and NOT `package.yaml`.** This is M8, and it is
       the single most important line-level decision in the file. The image's Stack is 3.3.1 with a
       different hpack; if `package.yaml` were present, Stack would regenerate the `.cabal` files
       inside the image with a different version header, and an entire class of confusing drift
       failures becomes possible. Copying only `.cabal` makes the image's Stack version
       structurally irrelevant to the drift gate. Write that reason into the file as a comment.

       COPY the seven `.cabal` files explicitly (one line each) plus `stack.yaml stack.yaml.lock`,
       then `RUN stack --system-ghc --no-install-ghc build --only-dependencies` — **with NO
       `--mount=type=cache` on this line.**

       This is the correction that makes the `.cabal`-only layer worth having. A BuildKit cache
       mount is scratch space deliberately EXCLUDED from the committed layer, and `/root/.stack`
       is exactly where Stack's package DB lives. Mounting it here means the dependency layer
       compiles the whole Chart/cairo tree and then stores NOTHING — and the source layer
       recompiles it all from an empty mount. Worse, masking `/root/.stack` can hide the base
       image's own Stack configuration. Bake `~/.stack` into the layer instead; that is the
       entire reason for copying `.cabal` files before the sources.

    4. **Runtime stage `debian:bookworm-slim`** plus `libgmp10 ca-certificates`, **`ENV LANG=C.UTF-8`**,
       a non-root `useradd --system --uid 10001 --user-group bridge`, `COPY --from=builder /out/evm-spec-bridge`,
       `USER bridge`, `ENTRYPOINT ["/usr/local/bin/evm-spec-bridge"]`.
       The comment must state the measured `ldd` result from Task 3 and note that Phase 11 revisits
       it once the shipped binary links `cfmm-adapter`.

    `--system-ghc --no-install-ghc` are passed on the COMMAND LINE, not written into `stack.yaml` —
    they are correct inside the image and wrong for a contributor whose local GHC differs.

    Do NOT put a cache mount on the dependency layer (see above). If you keep one anywhere, it is
    on the SOURCE build only, and add a comment recording that it helps local iteration
    but are NOT persisted by `cache-to: type=gha` (MEDIUM confidence), so CI relies on the
    `.cabal`-only dependency layer instead.
  </action>
