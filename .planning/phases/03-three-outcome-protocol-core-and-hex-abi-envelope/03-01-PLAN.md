  <name>Task 1: Why the guard enum cannot come from the spec</name>
  <read_first>
    - .planning/phases/03-three-outcome-protocol-core-and-hex-abi-envelope/03-CONTEXT.md (section "Guard identity representation")
    - stack-core.yaml
    - scripts/seam-guard.sh
  </read_first>
  <teaching>
    INTEG-02 wants a closed guard enum where adding a guard is a compile error. The obvious way to
    get that is to reuse the spec's own guard type — it is already closed, already authoritative.

    We cannot. `Bridge.Protocol` lives in `components/protocol`, a CORE component, and CFMM-01
    forbids a core component from depending on the spec package. That is not a policy someone might
    waive: `stack-core.yaml` omits the spec entirely, so the dependency fails to RESOLVE. We watched
    it fire in 01-04 with `[S-4804]`.

    So the enum is OURS, and `cfmm-adapter` — the only component permitted a spec edge — maps the
    spec's guard result onto it with an **exhaustive match**. That match IS the compile error
    INTEG-02 asks for: a new guard in the spec makes the adapter stop compiling.

    This is PROJECT.md's RPC-02 split working as designed. The spec EVALUATES guards; the bridge
    only MAPS them. Phase 11 criterion 4 is that this is "verifiable by inspection of a single
    mapping function" — that function is what this design creates.
  </teaching>
  <verify>
    ./scripts/seam-guard.sh; echo "seam exit=$?"
    grep -n "packages:" -A8 stack-core.yaml
  </verify>
  <action>
    Walk the user through the constraint and confirm they can state:
      - why the enum cannot be derived from the spec's type (resolution failure, not preference)
      - where the INTEG-02 compile error actually lands (cfmm-adapter's exhaustive match)
      - why naming a constructor after a cfmm guard does NOT trip the seam (no package dependency)
    Record in 03-01-PROBE-NOTES.md under "Guard enum placement".
  </action>
  <acceptance_criteria>
    - 03-01-PROBE-NOTES.md contains a "Guard enum placement" section stating the constraint and where the compile error lands
    - The user has confirmed all three points
  </acceptance_criteria>

<task type="auto" id="03-01-T3">
  <name>Task 3: The three-outcome sum type</name>
  <read_first>
    - components/protocol/src/Bridge/Protocol.hs (the placeholder being replaced)
    - .planning/phases/03-three-outcome-protocol-core-and-hex-abi-envelope/03-CONTEXT.md (Phase Boundary and Specific Ideas)
  </read_first>
  <teaching>
    PROTO-01: "no partial function able to produce one outcome from another". Two things follow.

    First, three CONSTRUCTORS, not a record with a status field. A status field permits
    `outcome { status = Success }` on a value carrying rejection data. Constructors do not.

    Second, `-Wincomplete-patterns` must be clean and must STAY clean. A non-exhaustive case over
    the outcome type is exactly the partial function PROTO-01 forbids — it silently drops an
    outcome rather than mapping it wrongly, which is worse because there is nothing to inspect.

    Note what TransportFailure means here. On the wire it is NOT a payload — Foundry gives us one
    untyped revert and a transport failure never arrives as a successful response at all. It exists
    in the Haskell type because the *server* can classify its own faults, and because Phase 4's
    fixture methods must be able to produce one deliberately.
  </teaching>
  <action>
    Replace `components/protocol/src/Bridge/Protocol.hs` with a real module exporting:

    - `data SpecOutcome a = SpecSuccess a | SpecRejection GuardId | SpecTransportFault FaultCode`
      (three constructors; name the type and constructors as you judge best, but three they must be)
    - `data GuardId = ...` — the closed, NAMED cfmm guard enum. Derive `(Eq, Show, Enum, Bounded)`.
      `Bounded`/`Enum` matter: they let a test enumerate every guard and assert total coverage.
    - `newtype FaultCode = FaultCode Word16` with named constants, for protocol-level faults
    - `protocolVersion :: Word16` — a SINGLE constant, defined once. Not a literal repeated at
      construction sites.
    - `ghc-options: -Wall -Wincomplete-patterns` in `package.yaml` for this component

    Keep the module free of any JSON or ABI concern — encoding is 03-02 and 03-03. This module is
    types only.
  </action>
  <verify>
    grep -n 'protocolVersion' components/protocol/src/Bridge/Protocol.hs
    grep -c 'Bounded' components/protocol/src/Bridge/Protocol.hs
    stack build --pedantic 2>&1 | grep -i 'incomplete-patterns' ; echo "incomplete-pattern warnings above (none expected)"
    stack build --pedantic; echo "build exit=$?"
  </verify>
  <acceptance_criteria>
    - `Bridge/Protocol.hs` defines a sum type with exactly THREE constructors for the outcome
    - A guard enum exists deriving `Bounded` and `Enum`
    - `protocolVersion` appears exactly ONCE as a definition: `grep -c '^protocolVersion' ` returns 1
    - `package.yaml` for protocol contains `-Wincomplete-patterns`
    - `stack build --pedantic` exits 0 with NO incomplete-pattern warnings
    - The module imports nothing from `Data.Aeson` or `Data.Solidity` — types only
  </acceptance_criteria>
  <done>Three outcomes are three constructors, the guard enum is closed and enumerable, and protocolVersion is defined once.</done>
