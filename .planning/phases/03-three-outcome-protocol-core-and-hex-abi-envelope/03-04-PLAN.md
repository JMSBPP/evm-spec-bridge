<objective>
Channel discipline as a property of the types: a spec rejection **cannot be constructed** into the
JSON-RPC `error` channel.

Purpose: PROTO-02. `PITFALLS.md` Pitfall 1 MEASURED that a well-formed JSON-RPC `error` object, an
HTTP 500, a refused connection and the 45 s timeout all reach Solidity as the identical revert
selector `CheatcodeError(string)` = `0xeeaa9e6f`, differing only in unstable English text. A
rejection on that channel is therefore INDISTINGUISHABLE from a dead server — which destroys the
Core Value.

Output: `Bridge.JsonRpc` built on `json-rpc-1.1.2`'s `Network.JSONRPC.Data`, whose rejection-building
function returns `Response` and has no `ResponseError` in reach.
</objective>

  <name>Task 2: The rejection builder whose return type is Response</name>
  <read_first>
    - components/jsonrpc/src/Bridge/JsonRpc.hs (the placeholder; its comment was corrected 2026-08-28)

  </read_first>
  <teaching>
    03-CONTEXT names the move this phase makes: from "remember rejections go in `result`" to
    "a rejection cannot be constructed into the `error` channel". The mechanism is a return type.

    `Network.JSONRPC.Data` gives us `Response` and `ResponseError` as SEPARATE constructors of the
    same sum. That is the lever. A function whose signature is `... -> Response` — the constructor,
    not the type — cannot return a `ResponseError`, and every caller that wants to serve a rejection
    must go through it.

    The `error` channel is not unused. It is RESERVED: `errorMethod` (-32601) for an unknown method,
    `errorParams` (-32602) for malformed params, `errorParse` (-32700) for unparseable input. Those
    are protocol faults — the caller sent something the protocol does not define. None of them can be
    produced from a `SpecOutcome`, because a `SpecOutcome` is what the protocol produced when it
    WORKED. Keeping the fault constructors in a separate function with a separate input type is what
    makes that structural instead of remembered.
  </teaching>
  <action>
    Rewrite `components/jsonrpc/src/Bridge/JsonRpc.hs` exporting:

      outcomeResponse :: Id -> SpecOutcome ByteString -> Either EnvelopeError Response
        -- ALL THREE outcomes, rejection included, become `Response` carrying the hex envelope
        -- from 03-03 in the `result` field. Never `ResponseError`.

      protocolFault :: Id -> ProtocolFault -> Response
        -- The ONLY function that constructs `ResponseError`. Its input is `ProtocolFault`,
        -- a type with NO conversion from `SpecOutcome`.

      data ProtocolFault = UnknownMethod Text | BadParams Text | ParseFailure
        -- maps to errorMethod / errorParams / errorParse respectively

    Rules to hold in the code:
      - `outcomeResponse`'s body mentions `ResponseError` zero times.
      - There is no function anywhere of type `SpecOutcome a -> ProtocolFault` or
        `SpecOutcome a -> ErrorObj`.
      - The `result` field carries the `Hex0x` from 03-02 via its single `ToJSON` — not a `String`
        built by hand, and not a JSON object.
      - `Ver` is `V2` and the `Id` is echoed from the request, never invented. Note in a comment that
        alloy sends `"id":0`, measured in 02-01-PROBE-NOTES.

    Add a test stanza to `components/jsonrpc/package.yaml` (mirroring `abi-codec`'s from 03-03-T3).
    Regenerate and COMMIT the `.cabal`.
  </action>
