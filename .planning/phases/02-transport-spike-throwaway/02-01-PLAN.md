Create the one artifact of Phase 2 that outlives Phase 2: an **enforceable** Foundry pin.

Purpose: DIST-06's operative word is *enforceable*. A version sitting in a config file is a value
you can read. A `forge --version | grep -qF "$FOUNDRY_COMMIT" || exit 1` is a proposition that goes
red. This plan builds the second kind, and — following Phase 1's discipline — makes it fire before
trusting it.

Output: `.github/foundry-version`, `scripts/foundry-pin.sh`, wired into both `justfile` and CI.
</objective>

  <teaching>
    Three values, each defending a DIFFERENT failure — this is the part worth understanding, not
    copying:

      FOUNDRY_VERSION            — what to install. Defends nothing on its own.
      FOUNDRY_COMMIT             — the commit the release was built from. THIS is the assertion.
                                   Their comment: "a tag can in principle be re-cut, and '1.5.1'
                                   alone would not notice."
      FOUNDRYUP_INSTALLER_COMMIT — the installer itself. "An unpinned installer is an unpinned
                                   supply chain for the pinned toolchain."

    Shell-sourceable `KEY=value` is chosen deliberately over TOML/JSON: it has TWO consumers here —
    CI shell, and (Phase 8) the Haskell generator that stamps the version into the generated
    Solidity header. `KEY=value` costs a few lines to parse in Haskell and zero in shell. TOML
    would invert that cost onto the shell side, which is the awkward direction.
  </teaching>

      FOUNDRY_VERSION=v1.5.1

      FOUNDRYUP_INSTALLER_COMMIT=a27902ef04dcb43061fabf343365cb5afc95fc48

      - what each of the three values defends against
      - that it is consumed by `scripts/foundry-pin.sh` and, from Phase 8, by the Solidity header

<task type="auto" id="02-01-T3">
  <name>Task 3: Write scripts/foundry-pin.sh — two modes, because the two sides can see different things</name>
  <read_first>
    - scripts/seam-guard.sh (the established script convention: exits non-zero, names the offender)
    - .github/foundry-version (written in T2)
    - .planning/ROADMAP.md (Phase 2 criterion 3, which specifies what each side asserts)
  </read_first>
  <teaching>
    A single script with two modes, because CI and the local box can honestly assert different
    things:

      --check-format  (CI)    The file is sourceable, all three values present, FOUNDRY_COMMIT is
                              40 hex chars. Needs no forge and no network.
      (default)       (local) The above, PLUS `forge --version | grep -qF "$FOUNDRY_COMMIT"`.

    Why not run the binary assertion in CI too? Because forge is deliberately not installed there.
    Installing forge purely to assert that it is the forge you just installed is **circular** — it
    can only fail if `foundryup` itself is broken, and it costs an unmeasured install on every run.
    Asserting only what you can actually see is the honest form.

    Apply the Phase 1 rule: **exit code before greps.** Capture `forge --version` output AND its
    exit status; a `forge` that fails to run must not be mistaken for a version mismatch, and a
    grep over empty output must not be mistaken for either.
  </teaching>
  <action>
    Create `scripts/foundry-pin.sh`, executable, `set -euo pipefail`, following the shape of
    `scripts/seam-guard.sh`. It must:

    1. Resolve the repo root and source `.github/foundry-version`, failing with a clear message if
       the file is missing.
    2. Assert all three variables are non-empty (`: "${FOUNDRY_VERSION:?}"` style).
    3. Assert `FOUNDRY_COMMIT` matches `^[0-9a-f]{40}$` — reject a short SHA or a tag.
    4. If `--check-format` was passed: print what was validated and exit 0 here.
    5. Otherwise, run the binary assertion:
         - capture `forge --version` output and exit status SEPARATELY
         - if forge is absent or exits non-zero, fail with a message that says so explicitly —
           NOT "version mismatch"
         - then `grep -qF "$FOUNDRY_COMMIT"` over the captured output
    6. On mismatch, print the EXPECTED commit, the ACTUAL `forge --version` output, and the path to
       `.github/foundry-version`, then exit 1. The message must be actionable without reading the
       script.
    7. On success print a one-line confirmation naming the asserted commit.
  </action>
  <verify>
    test -x scripts/foundry-pin.sh
    ./scripts/foundry-pin.sh --check-format; echo "format mode exit=$?"
    ./scripts/foundry-pin.sh; echo "full mode exit=$?"
    grep -q 'set -euo pipefail' scripts/foundry-pin.sh && grep -q 'grep -qF' scripts/foundry-pin.sh
  </verify>
  <acceptance_criteria>
    - `scripts/foundry-pin.sh` exists and is executable (`test -x`)
    - `./scripts/foundry-pin.sh --check-format` exits 0
    - `./scripts/foundry-pin.sh` exits 0 on this box
    - Script contains `set -euo pipefail`
    - Script contains `grep -qF`
    - Script contains a 40-hex-char validation pattern (`[0-9a-f]{40}`)
    - Script captures forge's exit status separately from its output — verified by reading the
      script with the user, not by grep alone
  </acceptance_criteria>
  <done>The assertion script exists in both modes and exits 0 on this box.</done>
</task>

<task type="checkpoint:human-verify" id="02-01-T4" gate="blocking">
  <name>Task 4: Make the assertion FIRE, then restore byte-identically</name>
  <read_first>
    - scripts/seam-negative-test.sh (the three-stage CONTROL / NEGATIVE / CONTRAST pattern from 01-04)
    - scripts/foundry-pin.sh (written in T3)
  </read_first>
  <teaching>
    Phase 1's rule: **a guard nobody has seen fire is a guard being trusted, not verified.** The
    seam guard got a full negative test plus a meta-check for exactly this reason.

    There is a second, subtler failure this catches. A script that exits 0 unconditionally — a
    stray `|| true`, a grep over an empty string, a `set -e` that does not apply inside a pipeline —
    passes every positive test perfectly. The ONLY way to distinguish "the assertion passed" from
    "the assertion cannot fail" is to make it fail on purpose.

    Restore byte-identically afterwards. `git diff --exit-code` is the proof, not memory.
  </teaching>
  <action>
    Perform three stages, recording each in 02-01-PROBE-NOTES.md with its exact command and output:

    CONTROL   — `./scripts/foundry-pin.sh` on the clean tree. Record exit status (expect 0).

    NEGATIVE  — In a scratch COPY of the file (or via a temporary edit that is reverted in the same
                task), change the last character of `FOUNDRY_COMMIT`. Re-run. Record exit status
                (expect non-zero) and the full failure message. Confirm the message names the
                expected commit and shows the actual `forge --version`.

    CONTRAST  — Restore, then delete `FOUNDRY_VERSION` from the file and re-run. Expect a DIFFERENT
                failure — a missing-variable error, not a commit mismatch. This distinguishes "the
                guard fired for the reason we think" from "the guard fires at anything".

    Then restore and prove it: `git diff --exit-code .github/foundry-version` must exit 0.
  </action>
  <verify>
    ./scripts/foundry-pin.sh; echo "CONTROL exit=$?"
    # NEGATIVE and CONTRAST stages are performed interactively; record each exit status
    git diff --exit-code .github/foundry-version; echo "restored clean exit=$?"
  </verify>
  <acceptance_criteria>
    - 02-01-PROBE-NOTES.md contains all three stages with exact commands, exit statuses and output
    - The NEGATIVE stage recorded a NON-ZERO exit status
    - The NEGATIVE failure message quoted in the notes names the expected commit
    - The CONTRAST stage recorded a DIFFERENT failure message from the NEGATIVE stage
    - `git diff --exit-code .github/foundry-version` exits 0 after restoration
    - `./scripts/foundry-pin.sh` exits 0 again after restoration
  </acceptance_criteria>
  <done>The assertion was SEEN to fail on a corrupted commit, to fail differently on a missing value, and the file was restored byte-identically.</done>
</task>

    "Restore Stack cache" step:

      - name: Foundry pin well-formedness (DIST-06)

    Add a comment in the workflow stating that the binary assertion is deliberately NOT run here
    because forge is not installed in CI, and that installing it solely to assert it would be
    circular.

    Do NOT add a foundry install step. Do NOT add a forge job.
