<task type="checkpoint:decision" id="02-04-T1" gate="blocking">
  <name>Task 1: What this probe can and cannot establish</name>
  <read_first>
    - .planning/research/ARCHITECTURE.md (section 612)
    - .planning/phases/02-transport-spike-throwaway/02-VALIDATION.md (Known Validation Gaps — the first bullet)
  </read_first>
  <teaching>
    **Content-Type sits at layer ① and cannot corrupt a value.** It is a MIME label on the response
    body, carrying no structural information. Foundry's coercion — the lossy, value-dependent step —
    is layer ③, and it operates on the parsed JSON regardless of what the header claimed. So the
    only thing Content-Type can do is let the whole call through, or kill it outright. Binary.

    **The probe must not have a pre-written answer.** VALIDATION.md's first gap says it directly:
    the acceptance criterion is *"the outcome is recorded with its conditions"*, NOT *"the call
    succeeds"*. If we write a criterion asserting `text/plain` fails, and it succeeds, we will be
    tempted to call the probe broken rather than the assumption wrong. A probe whose expected result
    is already written down is not a probe.

    **Three rows, because two of them answer different questions.** `text/plain` asks "is a WRONG
    type rejected". Absent asks "is a MISSING header rejected". A client can enforce one and not
    the other, and collapsing them would hide that.

    **What it will NOT establish:** anything about the consumer's runner, about proxies, about
    HTTP/2, or about behaviour under load. One host, one OS, one observation each.
  </teaching>
  <action>
    Confirm with the user that they can state:
      - why Content-Type cannot produce a wrong value, only a failed call
      - why `text/plain` and absent are different questions
      - that both outcomes are acceptable results and neither is a failure of the probe
    Record the confirmation in 02-01-PROBE-NOTES.md.
  </action>
  <verify>
    # interactive: no command output required
  </verify>
  <acceptance_criteria>
    - The user has confirmed all three points
    - 02-01-PROBE-NOTES.md states explicitly that the probe has no expected outcome
  </acceptance_criteria>
  <done>The user can state that Content-Type cannot corrupt a value, that text/plain and absent are different questions, and that the probe has no expected outcome.</done>
</task>

<task type="checkpoint:human-verify" id="02-04-T4" gate="blocking">
  <name>Task 4: The hex envelope, byte-exact, against warp</name>
  <read_first>
    - .planning/research/PITFALLS.md (section 55-82, Pitfall 2 and the hex-payload rule)
    - spike/forge/test/Spike.t.sol (the decode from 02-03)
    - spike/stub-server/app/Main.hs (the hardcoded payload)
  </read_first>
  <teaching>
    This is the claim every later phase rests on: the bridge — not Foundry's heuristics — owns the
    encoding, because a `0x`-prefixed even-nibble hex string is the one JSON shape whose coercion is
    total and value-independent.

    It was measured against the `/tmp/orctest` stub. It has never been tested against warp. The
    stakes: if it does NOT hold here, Phase 3's entire envelope design needs rethinking, and better
    to learn that now than in Phase 9.

    "Byte-exact" means compared as bytes, not eyeballed as hex in a terminal. Compare with a keccak
    hash or an explicit length-plus-content check, so a truncation or a padding difference cannot
    pass visual inspection.

    Boundary values — zero, above 2^64, negative, empty, odd-nibble — are ROADMAP Phase 3
    criterion 2's job. Do not pull them forward. One payload, proven exactly.
  </teaching>
  <action>
    With the stub in `json` mode:

    1. Record the exact hex string the stub emits, character for character, and its nibble count.
    2. Record the raw returndata Solidity received.
    3. Record the bytes after the deliberate decode.
    4. Assert equality by hash: `keccak256(decoded) == keccak256(expected)` inside the test, and
       independently compute both hashes outside Solidity (e.g. with `cast keccak`) so the check
       does not rely solely on the code being tested.
    5. Record the byte LENGTH at each stage — emitted, received, decoded. A length change is the
       signature of a coercion that did not survive.

    Write a prose conclusion stating whether the hex envelope survived byte-exact, and whether this
    AGREES with PITFALLS.md:82.
  </action>
  <verify>
    cast keccak <decoded-hex>
    cast keccak <expected-hex>
    cd spike/forge && forge test -vvv; echo "exit=$?"
  </verify>
  <acceptance_criteria>
    - The emitted hex, raw returndata, and decoded bytes are each recorded verbatim with lengths
    - Equality is established by hash, and the hashes were computed by two independent means
    - The notes state whether the envelope survived byte-exact
    - The notes state whether this agrees with PITFALLS.md:82; a disagreement is called out
      prominently and execution stops for the user
    - No boundary values were tested — confirmed, with a note deferring them to Phase 3
  </acceptance_criteria>
  <done>The hex envelope was proven to survive Foundry's coercion byte-exact, with equality established by hash computed two independent ways.</done>
